Web Document Tool

A zero-dependency, static, richly-navigable documentation reader that turns a folder of Markdown files into a browsable site — with a hierarchical navigator, per-page contents, automatic section numbering, and a pannable/zoomable map of how the documents relate.

This document describes the proposed design for your review. Nothing is built yet. Section 17 lists the specific decisions I need from you before I start.

1Overview & goals

You drop Markdown files into a folder. The tool presents them as a documentation website: a pop-out hamburger tree of the whole library, a two-pane reading view (contents on the left, rendered document on the right), automatic hierarchical section numbers, a day/night theme, and a separate visual "map" that draws each document as a box and connects them by the relationships declared in each document's metadata.

Core experiences:

  • Read — pick a document from the tree; read it rendered, with a live table of contents.
  • Navigate the library — the hamburger drawer shows the whole document hierarchy.
  • Understand the shape of the knowledge — the graph view shows prerequisites ("assumed knowledge") and suggested reading order ("recommended next") as a navigable diagram you can pan, zoom, and click through.

2Principles & hard constraints

3System architecture

The whole system is a pure pipeline from authored Markdown to rendered page. The single most important architectural rule is that the Markdown parser is a pure string → HTML function — metadata extraction, sanitization, and section numbering are all layers around it, never inside it. That boundary is what lets us claim (and measure) 100% CommonMark compliance while still stripping styling, injecting section numbers, and reading custom metadata.

Discovery & loading — no build step, served model

The site runs behind Python's built-in HTTP server (serve.py, stdlib only — still zero third-party). There is no build step: the server serves files and answers directory listings; the browser discovers documents, fetches each one, strips its JSON metadata, and renders it. A single config.json can list several source folders, which the server mounts side by side and the app aggregates into one library.

ResponsibilityWhere it runs
Serve app/ + each configured source folder as static files; return directory listings as JSONserve.py — does no Markdown/metadata parsing
Discover .md files, read JSON metadata, render Markdown, build tree / graph / searchThe browser, client-side (per D1 & D4)
Consequence of "no build step, served"

Because everything is fetched over HTTP, the app uses ES modules and normal fetch() — the file:// restrictions that would have forced a build step and classic scripts simply don't apply. The trade-off: the browser fetches each document once on load to populate the tree, graph, and all-documents search (comfortable for tens–hundreds of docs). The server stays a dumb, config-driven file server.

5Authoring model & metadata

Each document is one .md file: a JSON metadata block at the very top, then a normal CommonMark body. The app strips the metadata block before a single byte reaches the parser, so it can never affect CommonMark compliance. It's wrapped in an HTML comment so that, even if a strip were ever missed, it stays invisible (a comment) rather than showing as text.

It captures exactly the fields you specified — title, a brief description, assumed knowledge (0..n), and recommended next pages (0..n). assumes and next reference other documents by their id/slug, which is what feeds the graph.

6Markdown engine (full CommonMark)

"Fully compliant" is defined as a measurable number: for every example in CommonMark's machine-readable spec.json (~650 cases), normalize(parse(md)) === normalize(expected). Target: 100%. The suite runs headlessly and gates every change, so compliance can't silently regress.

Full compliance forces the spec's own two-phase architecture — a single-regex-per-line translator provably fails hundreds of cases (nested emphasis like **a *b** c*, code-span vs emphasis precedence, reference links, tight/loose lists, the 7 HTML-block types):

  1. Block phase — a line-driven state machine builds the block tree (paragraphs, ATX + setext headings, fenced & indented code, block quotes, lists with lazy continuation, HTML blocks, thematic breaks, link reference definitions). Link-reference definitions are fully collected here before inline parsing, because a reference can point forward.
  2. Inline phase — over each leaf block's text: code spans, autolinks and raw inline HTML (consumed as opaque, giving correct precedence), then emphasis/strong/links resolved with the spec's delimiter-stack algorithm.

GFM extensions

IncludeDefer
Tables (a product requirement), strikethrough ~~…~~, task-list items - [ ], extended autolinks (bare URLs), GFM's disallowed-raw-HTML filter.Footnotes, <details> sugar, emoji shortcodes, @-mentions — disproportionate cost for a docs tool; can be added later.

Strikethrough is nearly free once the delimiter stack exists (~ is just another delimiter). GFM cases are tracked in a separate corpus so a table bug can't mask a CommonMark regression; we report two numbers.

Honest cost

A from-scratch compliant parser is real engineering — on the order of a few thousand lines with a long tail of edge cases. It's justified because the zero-dependency rule takes every existing library off the table, the complexity is bounded and well-documented, and the conformance suite means we always know exactly where we stand and never guess whether we're "done." We can ship useful at a high-90s pass rate and ratchet toward 100%.

Syntax highlighting

Fenced code blocks are highlighted with hand-written, zero-dependency tokenizers — no Prism, no highlight.js. A fenced block's info string (e.g. ```python) becomes class="language-python" on the <code> element, exactly as CommonMark/GFM prescribe (so the compliance suite still passes on raw output). Highlighting then runs as a post-sanitize, post-numbering DOM decoration: it reads the language, tokenizes the code's text, and wraps tokens in trusted <span class="tok-…"> elements — the same layering pattern as heading numbers.

Languages at launch: Python, Robot Framework, Makefile, shell, and Java, plus a generic fallback (strings / comments / numbers) for anything else and untagged blocks. Each is a small state-machine tokenizer; token colours are theme tokens, so highlighting adapts to day and night. Because highlighting operates only on already-sanitized text and emits only span wrappers, it adds no attack surface.

7HTML sanitization — styling rejected

CommonMark deliberately passes raw HTML through. Your requirement — HTML allowed, all styling rejected — is satisfied by a separate DOM-based sanitizer that runs after parsing and before injection. Because it's an app policy layer, the conformance suite runs against the unsanitized parser output, so the sanitizer can never lower the compliance score.

It parses the HTML into an inert document (no scripts run, no resources load), then walks it with a closed allowlist (deny by default):

RuleEffect
Drop style attributes; remove <style> subtreesKills all inline & embedded styling (the core requirement)
Drop class attributesNo author-controlled styling hooks (our own numbering classes are added after sanitizing, so they're trusted)
Drop every on* handler; remove <script>Event-handler & script XSS
Drop presentational attrs (align, bgcolor, color, width, height, border…)Legacy styling
URL scheme allowlist on href/src: http(s), mailto, relative/anchor onlyBlocks javascript:, vbscript:, data:, obfuscated variants
Allowed tags only (headings, p, ul/ol/li, a, img, code, pre, blockquote, table…, task-list input[type=checkbox][disabled]); dangerous elements (iframe, object, embed, form, base, meta, svg) removed as subtreesStructure preserved, attack surface removed

DOM-based (not regex) because a regex sanitizer over raw HTML is notoriously bypassable. This is security-critical code, so it gets its own XSS payload test corpus asserting nothing dangerous survives — and because it's app-layer, we can harden it without ever touching the compliance number.

One narrow, validated exception: the sanitizer preserves a class="language-…" value on <code>/<pre> elements (and strips every other class, everywhere). This is a semantic language hint, not a styling hook — authors still cannot supply CSS (<style> and inline style are gone), so nothing about "styling is rejected" changes; it simply lets the syntax highlighter (§6) pick the right grammar.

8Heading auto-numbering

Your Markdown contains no numbers. The renderer injects hierarchical numbers (1, 1.1, 1.2.1, 2…) for every heading h1–h6, in both the rendered content and the left-pane contents — as a post-parse decoration on the sanitized DOM, so the Markdown is never mutated and compliance is untouched. (This very page is numbered by exactly this scheme.)

counters = [0,0,0,0,0,0]                 // one slot per h1..h6
for each heading of level L in document order:
    counters[L-1] += 1                   // bump this level
    for d in L..5: counters[d] = 0       // reset deeper levels
    for k in 0..L-1:                      // graceful skip (h1 → h3):
        if counters[k] == 0: counters[k] = 1   //   fill implied ancestors
    label = counters[0..L-1].join('.')   // e.g. "1.2.1"
    prepend label to heading; give heading a stable slug id
    toc.push({ level:L, number:label, text, id })

Content numbering and TOC numbering come from a single pass over the same DOM using the same ids, so they can never drift out of sync, and every TOC entry links to its identically-numbered heading.

9App shell & navigation

A deliberately simple shell: a header, a footer, and a contents section that is a horizontal two-pane split. There are three distinct navigation surfaces, and keeping them distinct is important:

SurfaceScopeNavigatesBuilt from
Hamburger tree (pop-out drawer)Whole libraryBetween documentsThe docs/ folder hierarchy
Left-pane contents (TOC)Current documentWithin the page (scrolls to a heading)The current doc's headings + injected numbers
Graph view (overlay)Whole libraryBetween documents, spatiallyMetadata edges: assumes + next

Plain-language labels bake the distinction into the UI: hamburger = "All documents", left pane = "On this page", graph = "Map". The header carries the site title, the hamburger button (left), and a right-hand cluster with the graph toggle and the theme toggle. The footer carries, straight from the current document's metadata, its assumed-knowledge links (read first) and its recommended-next links — each of which may be several.

Search (D6) lives in three places, each scoped to its surface: an in-document search in the reading pane (find & jump within the current doc), an all-documents search in the hamburger drawer (filters the whole library by title + content), and a node search in the graph / mini-map (locates a document box and centers it).

10Wireframes

11The relationship graph

This is the most algorithmically interesting part, and it's built entirely by hand. It draws the documents as boxes and the metadata relationships as directed edges, then lets you pan, zoom, and click through.

  • Substrate: SVG. At our scale (tens to low-hundreds of docs) SVG gives free hit-testing (every box is a real element with a click handler), crisp text at any zoom, and declarative edges/arrowheads — exactly the things Canvas would make us reimplement.
  • Layout: a hand-rolled layered (Sugiyama-lite) algorithm. Edges flow in the learning direction (prerequisite → dependent). Stages: break any accidental cycles from bad metadata (drawn, but flagged, never hidden) → assign layers by longest-path → order within layers by the barycenter heuristic to reduce crossings → assign coordinates → route edges. Disconnected clusters are laid out separately and packed. Deterministic, so the same docs always produce the same map (important for you and for tests).
  • Pan/zoom: one transform on the SVG viewport group. Wheel-zoom is anchored at the cursor (the point under the pointer stays put), drag-to-pan uses pointer capture, zoom is clamped, and a "fit to view" button frames everything. Arriving from a document centers that document's box.
  • Edges: smooth bezier curves with arrowheads; prerequisites solid/cool, recommended-next dashed/warm — distinguished by both colour and dash so they read in grayscale and for colour-blind users.
  • "Smarts": reciprocal edges are de-duplicated; hovering a box highlights its neighbourhood and dims the rest; optionally it can highlight the full set of transitive prerequisites ("everything to read first"); a reference to a missing document becomes a clearly-marked placeholder plus an entry in a diagnostics list — the graph doubles as a link-checker.

12Day / night theming

All colour is expressed as CSS custom properties. <html data-theme="light|dark"> selects the palette; an inline head script resolves the theme before first paint (no flash), preferring a saved choice, then the OS prefers-color-scheme. The header toggle flips it and persists to localStorage. Every token pair meets WCAG AA contrast. 13Responsive & accessibility

  • Responsive: ≥1024px two-pane; 640–1023px the contents narrow or collapse to a disclosure; <640px a single column with the contents as an "On this page" disclosure and full-screen overlays for the tree and graph.
  • The tree is a real ARIA tree (role="tree"/treeitem, roving tabindex, arrow-key navigation, aria-expanded, aria-current="page").
  • Focus management: opening the drawer or graph traps focus and returns it to the trigger on close; switching documents moves focus to the new h1 and announces via a polite live region.
  • Motion & contrast: all transitions respect prefers-reduced-motion; a visible focus ring on every control in both themes; a skip-to-content link.

14Testing (Playwright)

Tests use Playwright through its Python binding (pytest-playwright) — no Node, no npm, keeping the whole toolchain to Python + a browser. They live only in tests/; Chromium installs outside the repo via playwright install. Tests run over HTTP against serve.py (started as a fixture, bound to 127.0.0.1 for a stable origin). Two test streams:

  • Compliance harness: a vanilla-JS page loads the parser and runs every vendored CommonMark spec.json case (and a separate GFM corpus) in the browser, diffs normalized HTML, and writes the pass-rate to the DOM; a Playwright test opens it and asserts the rate (ratchet: it can only go up). The parser executes in a real browser engine — never Node.
  • End-to-end suite: tree builds correctly; a doc renders; every Markdown feature renders; the sanitizer positively neutralizes styling/scripts (assert window.__pwned stays undefined and no dialog fires, not merely that a tag is absent); metadata parses; heading numbers match between content and TOC; TOC links scroll; theme toggle persists across reload; tree navigation updates the URL and deep-links work; the graph renders nodes+edges, pans, zooms, and node-clicks open the right doc; missing references degrade gracefully.

The graph is made deterministic and non-flaky by design: a ?test=1 mode disables animation and uses fixed layout, and the transform state is exposed as data-scale/data-tx/data-ty with stable data-node-ids, so tests assert exact numbers instead of pixel-diffing. A data-app-ready flag gates every assertion so nothing races startup. The demo corpus is the test fixture set (a normal doc, a Markdown kitchen-sink, an XSS-payload doc, a deep-nesting doc, and a broken-links doc), so the tool ships with meaningful sample content.

18Requirements traceability

You can build a requirement hierarchy on top of this exact system — Requirements.md pages whose requirements are tracked and traced across every document — by reusing what the design already provides: fenced-block transforms (like syntax highlighting), the metadata index, the relationship graph, search, deep-links, and theming. Almost nothing here is new machinery; it is the same capabilities pointed at requirements.

Authoring a requirement

A requirement is a fenced code block with the info string requirement — valid CommonMark (so compliance is untouched), which the app turns into a requirement card using the very same post-sanitize hook the syntax highlighter uses. A page holds as many as you like, under normal headings.

```requirement
{
  "id": "FR-012",
  "title": "Users can reset their password via email",
  "type": "functional",
  "status": "approved",
  "parents": ["SR-004"],
  "satisfiedBy": ["design/auth-flow", "FR-013"],
  "verifiedBy": ["TC-101", "TC-102"],
  "tags": ["auth", "security"]
}
```

A Requirements.md page is just a normal document (with the usual <!--meta--> header) that contains these blocks. Requirement ids are author-assigned and globally unique; a collision is a flagged warning.

The trace model

FieldMeaning & direction
id, title, type, status, tagsIdentity + classification — drives colour, filtering, and the coverage dashboard.
parentsHigher-level requirements this derives from — the hierarchy backbone (upward). Children are computed as the inverse.
satisfiedByWhat fulfils it — may reference other requirement ids or document ids, so requirements trace directly into the documentation.
verifiedByWhat verifies it — test / verification items, modelled as requirement blocks of type:"test" so verification lives in the same graph.

On load — in the same pass that already fetches every document for the tree and graph — the app scans each page for requirement blocks, parses them, and builds one global trace index (id → {page, anchor, fields, computed inverse-links}). Every trace target resolves against the requirement index first, then the document index; anything unresolved is flagged as a dangling reference — the same treatment as a broken document link. Each requirement is deep-linkable: #/<page>?req=FR-012.

What you get — the traceability views

Each is built by reusing a capability already in the plan:

  • Requirement cards — every block renders in place as a card: id badge, title, type + status pills, and clickable trace chips (Parents ↑, Children ↓, Verified by, Satisfied by) that jump — across documents — to the target requirement. Reuses the fenced-block transform + sanitizer + deep-links.
  • Requirement map — the §11 graph gains a "Requirements" mode: nodes = requirements, edges = parent→child (solid) and verify / satisfy (styled distinctly). Pan, zoom, node-search and neighbourhood highlighting all come for free. Reuses the graph engine.
  • Traceability matrix — a filterable table (requirements × parent / verification / satisfaction) with coverage cells and gaps highlighted. New view; a plain DOM table.
  • Coverage dashboard — totals, % verified, % satisfied, orphans (no parent), leaves with no verification, dangling references, status breakdown. New; a small summary panel.
  • Impact / trace — from any requirement, list and highlight the full upstream (all ancestors) and downstream (children + verifications). Reuses the graph's neighbourhood highlight.
  • Hierarchy outline & filter — the requirements as a collapsible tree by parent/child, filterable by type / status / tag. Reuses the tree + search patterns.

Integration & what is actually new

Reuses: the Markdown engine (fenced blocks), the sanitizer, discovery/metadata, the graph engine, search, deep-links, and theming. New pieces are small: a requirements.js module (extract → index → render cards → matrix + dashboard + graph feed), a requirements.css, and a "Requirements" entry point in the header. The requirements features switch on automatically for any document set that contains requirement blocks (or via a config.json flag).

Choices to confirm when we build it
  • Granularity — many requirement blocks per page (recommended) vs one requirement per document.
  • Verification — model test cases as requirement blocks of type:"test" so the whole V-model is one traceable graph (recommended), vs treating verifiedBy as external references only.
  • Trace types — the v1 set (parents, satisfiedBy, verifiedBy, plus an optional relatedTo); rename/extend to match your process (e.g. DOORS-style derives / refines / satisfies / verifies).
  • ID scheme — free-form author ids (FR-012) with uniqueness enforced (recommended).
