# Architecture

WebDocs is two cooperating halves that share almost no responsibility. A tiny
Python server *serves* documents and hands them to the browser as files. The
browser application *renders* them. Nothing on the server side ever transforms
Markdown; nothing on the client side ever touches the filesystem. Keeping that
line sharp is what lets the whole thing stay static, easy to reason about, and
almost free of dependencies — the one it does carry is described at the end of
this page.

## The rendering pipeline

Every document is processed by the same fixed sequence of stages. Each stage has
one job and hands a well-defined artifact to the next.

- **Extract requirement groups.** Before any Markdown parsing, the raw source is
  scanned for `<!--meta start … -->` / `<!--meta end … -->` pairs. The wrapped
  tables are pulled out so their ids and traces can be composed and later
  re-inserted as decorated requirement tables.
- **Parse Markdown.** The remaining source is handed to the CommonMark engine,
  which produces an HTML string. This is the heart of the tool; see
  [The CommonMark Engine](Docs/design/parser).
- **Sanitize.** The HTML is parsed into a DOM and walked against an allowlist.
  Styling and scripting are stripped — inline styles, `style` and `class`
  attributes, `script` elements, event-handler attributes, and dangerous URL
  schemes all go. The one exception is a single `class="language-*"` token on
  `<code>`/`<pre>`, which is kept (lowercased) as a hint for the highlighter and
  block renderers; every other class attribute is removed. The sanitizer is
  intentionally a *separate* pass from the parser, so the security boundary does
  not depend on parser correctness.
- **Number headings and build the contents.** Headings receive hierarchical
  numbers (`1`, `1.1`, `1.1.1`, …) and the same structure is mirrored into the
  on-this-page contents list.
- **Decorate.** Requirement groups become five-column trace tables — Requirement,
  Description and Trace To are authored, while Trace From and Verified By are
  computed inverse links. In-body links are then resolved, fenced `mermaid`
  blocks are turned into rendered diagrams by the pluggable block-renderer system
  (`renderBlocks`, which runs after link resolution and before highlighting), and
  finally code blocks are run through the appropriate per-language highlighter.
- **Inject.** The finished fragment is placed into the content pane and the
  contents list is populated.

```text
raw .md
  |
  v
[ extract requirement groups ]   pull <!--meta start … end--> tables aside
  |
  v
[ parse Markdown ]               CommonMark 0.31.2 + GFM  ->  HTML string
  |
  v
[ sanitize ]                     allowlist DOM pass; strip style + script
  |
  v
[ number headings + build TOC ]  1, 1.1, 1.1.1 …  mirrored in contents
  |
  v
[ decorate ]                     requirement tables + link resolution + block renderers (mermaid) + highlighting
  |
  v
[ inject ]                       into the content pane
```

The ordering matters. Requirement extraction runs first so table markup never
reaches the Markdown parser as ambiguous content. Sanitization runs *after*
parsing but *before* numbering and decoration, so numbers and highlight markup
are added to already-trusted DOM rather than being sanitized away.

## The app shell

The page is a single, static shell that the pipeline fills in.

- **Header** — the hamburger that opens the document tree and drawer search, the
  brand/site title and breadcrumb, an in-page *Find in page…* input, the
  New-document button (`+`), the Test-coverage toggle (the checkmark), the entry
  point to the map, and the theme toggle. A floating Edit button sits in the body
  for editing the current document.
- **Two-pane body** — an on-this-page contents list beside the rendered content
  column. The contents list is generated by the numbering stage and stays in
  sync with the headings.
- **Footer** — the multi-link footer.

The relationships between documents are also visualised in the map — the same
`assumes`/`next` metadata that orders your reading is drawn as edges there (see
[the map](Docs/features/map)).

Beyond rendering, the shell hosts two larger subsystems: a test-coverage view
(the checkmark button) with an interactive runner and an exportable HTML report,
and a hand-written WYSIWYG block editor (reached from the `+` and Edit buttons)
for authoring and editing documents.

## Config-driven discovery

The browser never guesses what documents exist. On load it fetches a single JSON
description of the library from the server.

- `serve.py` reads `config.json`, which names one or more **sources** — each a
  folder of Markdown plus a component id.
- The server emits `/site.json`, but that is only the site *config* plus its
  source mounts: the site title, default document, theme, enabled plugins, and
  for each source a name, url, component and optional testResults. It carries no document ids and no
  folder tree.
- Document discovery happens client-side. The client fetches `/site.json`, then
  walks each source's url on demand via `GET /docs/<source>/` directory listings
  (JSON `entries`), recursing into subfolders and stripping `.md` to form
  document ids. From those it builds the document tree and search index, then
  fetches each document's raw Markdown on demand and runs it through the
  pipeline.

Because discovery is just "list the files as JSON", the server stays a thin
stdlib script. See [Configuration](Docs/reference/config) for the `config.json`
fields and how a source maps a name and component onto a folder.

## The dependency principle

The browser application carries exactly one piece of third-party code: a compiled
Svelte 5 runtime, which the interactive chrome — the drawer, the header controls,
the edit controls, the map mode selector, the coverage panels — was moved onto
after hand-wiring DOM updates across those views became the largest single source
of the reader's state bugs. Nothing else came with it. The parser, sanitizer,
highlighters, the optional block-renderer plugin system, map renderer, search
client, WYSIWYG editor, and theming layer are all still hand-written, and no
library replaced any of them. They are written in TypeScript now rather than
JavaScript, but that is a change of language, not of authorship: the same
from-scratch code, with its types finally stated.

That runtime is compiled in rather than fetched. `app/build/islands.js` — around
142 kB raw, 40 kB gzipped, built from the components in `app/svelte/` — is
**committed to the repository**, so a clean clone runs on a Python interpreter
and nothing else: no Node.js, no `npm install`, no network. `npm run build` is a
step for someone changing the UI, not for anyone authoring a document, reading
one, or running the server. Both halves of that arrangement are held in place by
the test suite, which fails if the committed bundle drifts from its sources or if
the package manifest's runtime `dependencies` object stops being empty; see
[the system requirements](Docs/requirements/system) for the rows those tests
verify.

The same arrangement covers the rest of the browser code. The modules live in
`src/js/` as TypeScript and are compiled into `app/js/` as JavaScript, which is
what `app/index.html` actually loads — one source file becomes exactly one served
module at the same path, with its import specifiers untouched, so the browser
resolves the same module graph it always did. That output is committed too, for
the same reason the bundle is.

So there are two generated trees in the repository, and it is worth being blunt
about what that costs: `app/js/` is no longer somewhere to edit. Changing browser
behaviour means editing `src/js/` and running a build. Markdown, CSS and the
server are unaffected — those are still edit-and-refresh, with no toolchain in
sight.

`serve.py` keeps the original rule outright: the Python standard library, with no
package to install. Playwright, driven from Python, exists purely to run the
automated tests and never ships to a reader. This is a constraint, not an
accident — it keeps the tool auditable, portable, and free of the supply chain
that a documentation reader has no reason to carry — and the single exception
above was made once, deliberately, rather than by drift.
